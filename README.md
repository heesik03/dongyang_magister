# Magister

**작품의 설정과 원고를 비교하고, 작가의 판단을 다음 검토에 반영하는 AI 창작 검토 서비스**입니다.

## 프로젝트 소개

장기 연재에서는 인물의 능력이나 성격, 세계관 규칙, 이전 회차의 사건을 모두 기억하며 새 원고를 검토하기 어렵습니다. Magister는 한국어 소설·웹소설 작가가 작품별 설정과 회차 원고를 관리하고, 공개 전에 설정 충돌과 설명이 부족한 전개를 확인할 수 있도록 돕는 프로젝트입니다.

작가가 확정한 설정과 선택한 이전 원고를 검토 기준으로 삼습니다. AI가 충돌 가능성을 발견하면 문제 문장과 관련 설정·원고의 위치, 판단 이유와 수정 방향을 함께 보여줍니다. 단순한 문장 교정을 넘어 작품 고유의 맥락을 확인하는 데 초점을 둡니다.

핵심은 **작가의 판단이 쌓이는 검토 흐름**입니다. 작가는 결과를 수용하거나 보류하고, 반전이나 능력 변화처럼 의도한 전개는 ‘의도된 설정’으로 기록할 수 있습니다. 저장된 판단과 적용 사유는 다음 회차 분석의 참고 정보가 됩니다. 이때 특정 장면의 예외를 모든 상황에 적용하거나, 비슷한 충돌을 무조건 무시하지 않도록 합니다.


## 핵심 기능과 범위

아래는 개발 목표이며, 현재 구현 상태는 별도로 표시합니다. 첫 MVP는 한국어 텍스트와 작품별 설정 분석에 집중합니다.

| 기능 | 제공할 경험 | 우선순위 |
| --- | --- | --- |
| 작품·설정집 관리 | 작품별 인물·능력·세계관 규칙을 등록하고 확정 설정과 아이디어 구분 | P0 |
| 회차별 원고 관리 | 원고를 입력·수정하고 분석에 참고할 이전 회차 선택 | P0 |
| 설정 충돌 분석 | 새 원고와 확정 설정·이전 원고의 충돌 후보 및 문제 위치 확인 | P0 |
| 인물 개연성 검토 | 성격·목표와 행동·대사를 비교해 설명 보완이 필요한 부분 확인 | P0 |
| 검토 리포트·판단 반영 | 원문·근거·수정 방향을 확인하고 수용·보류·의도된 설정과 사유 저장 | P0 |
| 사건 타임라인 | 주요 사건과 시점을 카드로 정리하고 근거 원문 확인·시점 수정 | P1 |

MVP의 우선순위는 설정 충돌 검토와 작가 판단 반영입니다. 사건 타임라인은 P1으로 구분합니다. 자동 원고 집필, 이미지 인식, 실시간 공동 편집, 인물 관계도는 첫 MVP에 포함하지 않습니다.

## 사용 흐름

1. 작품의 제목·장르를 등록하고 인물·세계관 설정의 확정 여부를 지정합니다.
2. 회차 원고를 입력하고 분석에 참고할 설정과 이전 원고 범위를 선택합니다.
3. 검토 결과에서 문제 문장, 관련 근거, 판단 이유와 수정 방향을 확인합니다.
4. 결과를 수용·보류하거나 의도된 설정으로 처리하고 판단 사유를 기록합니다.
5. 원고를 수정하거나 새 회차를 검토할 때 저장된 판단을 함께 참고합니다.

## Gemini 활용

AI 분석에는 **Google Gemini API**를 사용할 예정입니다. 작품별 확정 설정, 선택한 원고, 저장된 작가 판단을 함께 참고해 검토 후보를 구성합니다.

- **관련 정보 추출:** 원고의 등장인물·행동·사건을 파악하고 비교할 설정과 이전 원고 후보를 찾습니다.
- **설정·개연성 검토:** 확정 설정과 원고를 비교해 충돌 가능성과 설명이 부족한 지점을 찾고 검토 질문을 만듭니다.
- **리포트 구성:** 문제 문장과 근거를 연결해 판단 이유와 수정 방향을 제시합니다.
- **작가 판단 반영:** 저장된 의도·예외와 적용 범위를 다음 분석의 참고 정보로 활용합니다.
- **사건 추출(P1):** 주요 사건과 시간 표현을 정리해 타임라인 초안을 만듭니다.

AI 결과는 확정 판정이 아닌 검토 후보입니다. 인물의 변화나 반전 자체를 오류로 단정하지 않고, 근거가 부족하면 판단을 유보합니다. 결과에 포함된 설정 ID와 원문 위치를 서버에서 확인하고 원고 버전과 연결하며, 설정 변경과 최종 판단은 작가가 결정하도록 설계합니다.

## 기술 구성과 개발 상태

| 영역 | 구성 |
| --- | --- |
| 프런트엔드 | React 19.2 계열, TypeScript 6.0 계열, Vite 8.3 계열, ESLint, pnpm |
| 백엔드 | Java 21, Spring Boot 4.1.1, Gradle Wrapper, Spring MVC, JPA, Bean Validation |
| 데이터베이스 | MySQL 사용 예정, 드라이버 의존성 포함 |

프런트엔드의 회원가입·이메일 로그인·로그아웃·내 정보 조회는 세션 인증 API에 연결했습니다. 세션은 1시간 미사용 시 만료되며 Gemini API도 인증이 필요합니다. 작품·설정집의 생성·조회·수정은 서버 API에 연결되어 있습니다. 원고·검토 판단·타임라인은 서버 문서로 저장하며, AI 검토는 작업 ID로 상태와 결과를 조회하는 비동기 API에 연결했습니다. 프런트엔드는 `frontend/`에서 `pnpm install --frozen-lockfile` 후 `pnpm dev`로 실행합니다.

상세 요구사항과 일정은 [Notion 프로젝트 기획서](https://app.notion.com/p/_Magister-3eac29dbef40809b8150f5dc8e403d2e)에서 관리합니다.

## 백엔드 공통 응답

API 응답은 `success`, `code`, `message`, `data`, `errors`를 제공합니다. `code`는 서버 내부에서 `ResponseCode` 타입으로 관리하며, 성공은 `SuccessCode`, 실패는 `ErrorCode` 구현과 연결합니다. JSON의 `code`는 기존과 동일한 문자열입니다. 오류 응답은 `ErrorCode`에서 코드와 메시지를 함께 가져오며, HTTP 상태도 해당 오류 정의에 맞춥니다.

```json
{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해 주세요.",
  "data": null,
  "errors": [{ "field": "prompt", "message": "prompt is required" }]
}
```

공통 예외 처리기는 오류 코드와 HTTP 상태를 기록합니다. 4xx는 WARN, 5xx는 ERROR로 남기며 예외 메시지·원인·스택 트레이스·요청 본문은 기록하지 않습니다. 컨트롤러 로그는 요청 시작·종료와 소요 시간을 기록합니다. 추적 ID는 사용하지 않습니다.

### 프런트엔드 API와 상태 구조

- `shared/httpClient.ts`: `/api` 기본 경로, 세션 쿠키, CSRF, 공통 오류·응답 처리
- `features/auth/authClient.ts`: 회원가입·로그인·로그아웃·현재 세션 조회
- `features/works/workClient.ts`, `features/settings/settingClient.ts`: 작품 및 작품별 설정 요청
- `workResponse.ts`, `settingResponse.ts`: 외부 응답 검증과 화면 모델 변환
- `useAuthStore.ts`, `useWorksStore.ts`: 화면 간 공유 상태. 폼·선택·모달은 컴포넌트 상태로 관리

목록 조회에는 `workClient.list({ keyword, genre, page, signal })`처럼 이름 있는 옵션을 사용합니다. 서버 응답을 타입 단언으로 통과시키지 않고 파서로 검증합니다. 작품·설정의 런타임 샘플 데이터는 없으며 API 실패 시 오류를 표시합니다. 이전 버전에서 사용자가 브라우저에 저장한 작품은 자동 업로드하지 않고 보존합니다.

백엔드 공통 응답 클래스는 Swagger 애너테이션과 이름이 겹치지 않도록 `ApiResult`를 사용합니다. JSON 필드와 HTTP 경로는 유지되며 OpenAPI 컴포넌트의 응답 스키마 이름은 `ApiResult`로 변경되었습니다.

### 원고 저장과 비동기 검토

- `GET/PUT /api/work/{workId}/workspace`: 원고·검토 근거·작가 판단·타임라인 문서. 저장은 `version`, `mutationId`, `content`를 전송합니다. 같은 ID·내용 재시도는 중복 저장하지 않고, 오래된 버전은 409로 거절합니다. 최초 문서는 version 0이며 첫 저장은 1입니다. 작품 메타데이터 버전과 문서 버전은 별개입니다.
- `POST /api/work/{workId}/analysis`: 저장된 원고의 `chapterId`, `workspaceVersion`, 선택한 `settingIds`/`previousIds`, 검토 항목과 `requestId`를 접수하고 202·Location을 반환합니다. 같은 requestId는 중복 실행하지 않습니다.
- `GET /api/work/{workId}/analysis/{id}`: QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED 상태 및 검증된 근거를 반환합니다.
- `POST /api/work/{workId}/analysis/{id}/cancel`: 대기 작업 및 실행 중 결과 반영을 취소합니다. 이미 전송한 공급자 요청의 비용은 취소되지 않을 수 있습니다. 서버 재시작 시 미완료 작업은 실패로 표시합니다.
- 모든 API는 작품 소유권을 확인합니다. 변경 요청은 세션 쿠키·CSRF 헤더가 필요하며 입력/권한/충돌/한도 오류는 400/401/403/404/409/429로 반환합니다. HTTP 요청 본문은 8MiB, 저장 문서는 200만 자, AI 입력은 20만 자로 제한합니다. 회차 최대 100개·회차당 20만 자·검토당 후보 최대 100개·사건 최대 1,000개입니다.
- AI 호출은 사용자별 시작 간격 5초와 전체 동시 2개 제한을 분리합니다. 비동기 대기열은 8개로 제한하며, 외부 호출 동안 DB 트랜잭션을 유지하지 않습니다. 현재 실행기는 단일 애플리케이션 인스턴스용이며 여러 서버로 확장할 때 별도 작업 큐·분산 제한이 필요합니다. 기존 `/api/gemini`는 짧은 텍스트 연결 확인용 동기 API로 유지합니다.
- 원고 입력은 즉시 화면에 반영하고 600ms 뒤 서버에 저장합니다. 탭 간 저장 알림과 서버 버전 검사로 덮어쓰기를 차단합니다. 실패 시 입력과 탭별 복구본을 보존하며, 충돌 화면에서 입력을 파일로 내리고 서버본을 선택할 수 있습니다. 페이지 종료 시 미저장 경고를 제공합니다.
- 기존 `magister.works.v1:*`, `magister.drafts.v1:*` 데이터는 자동 삭제·업로드하지 않습니다. 같은 작품의 서버 문서가 비어 있으면 **이전 초안·탭 복구본 불러오기**로 명시적으로 가져옵니다. 기존 브라우저 전용 작품은 원래 보관함에 남습니다.
- CSRF 토큰은 메모리에만 캐시하고 동시 조회를 공유합니다. 로그인·로그아웃·401·403에서 폐기하며 변경 요청은 자동 재전송하지 않습니다.
- AI 전송은 분석 범위 화면의 동의 후에만 실행합니다. 원고·선택한 확정 설정·이전 회차·해당 회차의 기존 판단을 Gemini에 보내며, 반환된 설정 ID와 원문 인용을 서버에서 확인합니다. 설정과 원고는 자동 변경하지 않습니다.

설정 인덱스는 MySQL 임시 테이블 1만 건에 동일한 선택 쿼리를 실행해 확인했습니다. `(work_id,id)`는 추정 100행, `(work_id,kind,id)`는 25행이며 역방향 인덱스 탐색을 유지했습니다. 이에 kind 조회용 인덱스만 V6 마이그레이션으로 추가했습니다.
